Witnessed Hello

rvm-witness

Hash-chained 64-byte audit records. What the chain catches, what only the HMAC catches, and how fast emission actually is.

cargo run -p demo-01-witnessed-hello --release 
RVM Demo 1 — Witnessed Hello
Every privileged action emits a 64-byte hash-chained audit record.

1. Say hello, witnessed
-----------------------
seq  action           actor target  payload     prev_hash   rec_hash  signature
  0  PartitionCreate      0      1  "hello..."        0x0 0xabd4170c  valid    
  1  CapabilityGrant      1      2  "world..." 0xabd4170c 0xf0a60690  valid    
  2  PartitionDestroy     1      1  "!......." 0xf0a60690 0x7cb17d7b  valid    

3 records, 64 bytes each, 192 bytes total

2. Verify the untampered chain
------------------------------
verify_chain  -> OK, 3 records link cleanly
signatures    -> all valid

3. Tamper with a payload: rewrite history's content
---------------------------------------------------
Rewriting record 1's payload from "world" to "pwned"...

verify_chain  -> OK, 3 records link cleanly   <-- tamper NOT caught
signatures    -> INVALID at index 1                <-- tamper caught here

Why: `append` sets record_hash = compute_chain_hash(prev_hash, sequence).
It is derived purely from position in the chain, not from record contents --
despite the field docs describing it as a hash of bytes [0..44]. The unused
`compute_record_hash(data)` in hash.rs is what would cover contents.
So verify_chain proves *ordering*; only the HMAC signature proves *content*.
Using plain `append` instead of `signed_append` would leave this undetectable.

4. Tamper with ordering: renumber a record
------------------------------------------
Changing record 2's sequence from 2 to 7...

verify_chain  -> FAILED: corrupted record at seq 7   <-- caught

5. Throughput
-------------
append          1000000 iters in 314.25ms  =   314.2 ns/op
signed_append   1000000 iters in    1.63s  =  1631.8 ns/op

On the ~17ns figure in RVM's README: that is the FNV-1a path.
rvm-witness's *default* features include crypto-sha256, which is what you
get unless you opt out -- and it costs an order of magnitude more. Measured
on this machine:

    append, crypto-sha256 OFF (FNV-1a)   ~22 ns/op
    append, crypto-sha256 ON  (default) ~295 ns/op   <- rvm's own bench agrees

Both are honest numbers for different builds; the README just doesn't say
which one it is quoting. Re-run rvm's own bench to confirm:
    cargo bench -p rvm-benches --bench witness

Hello, Denied

rvm-cap · rvm-security

Capability minting, monotonic attenuation, GRANT_ONCE evaporating after one use, and denials landing in the audit log beside grants.

cargo run -p demo-02-hello-denied --release 
RVM Demo 2 — Hello, Denied
Capability tokens are the only way to touch a resource.

1. The hypervisor mints a root capability
-----------------------------------------
  root cap  index=0 gen=1  rights=READ|WRITE|GRANT
  agent tries the same          -> denied (GrantNotPermitted)

2. Delegate READ-only to the agent, then try to write
-----------------------------------------------------
  granted   index=1 gen=1  rights=READ

  agent reads the region             ALLOWED  (tier P1, witness seq 0)
  agent writes the region            DENIED   InsufficientRights: token holds READ

3. Monotonic attenuation: you cannot grant what you lack
--------------------------------------------------------
  agent grants itself READ|WRITE -> denied (GrantNotPermitted:
                                    its READ-only token has neither GRANT nor GRANT_ONCE)

4. GRANT_ONCE: authority that evaporates after one use
------------------------------------------------------
  minted    rights=READ|GRANT_ONCE
  1st delegation to partition 3 -> ok (index=3 gen=1)
  source rights are now READ   <-- GRANT_ONCE consumed
  2nd delegation to partition 3 -> denied (GrantNotPermitted)

5. The audit trail: denials are witnessed too
---------------------------------------------
seq  action            tier    cap_hash
  0  RegionShare        P1   0x1000002
  1  ProofRejected       -   0x1000002

Note: the denied write is in the log as ProofRejected with the same
cap_hash as the successful read -- so an auditor can see exactly which
token was presented for a refused operation, not just that something failed.

Three Ways to Prove Hello

rvm-cap · rvm-security

The P1/P2/P3 proof tiers: which one catches what, and what each costs.

cargo run -p demo-03-prove-hello --release 
RVM Demo 3 — Three Ways to Prove Hello
Same mutation, three depths of proof.

Delegation chain:  root(depth 0) -> mid(depth 1) -> leaf(depth 2)
The mutation is attempted with the leaf capability.

1. P1 and P3 on the happy path
------------------------------
  P1  handle + epoch + rights            PASS
  P3  full derivation chain to root      PASS

2. Which tier catches what
--------------------------

  Case A: token lacks EXECUTE
    P1  FAIL (P1: insufficient rights)
    P3  PASS
        ^ rights are a P1 concern. P3 does not look at rights at all,
          so it passes -- the tiers are additive, not ordered by strictness.

  Case B: an ancestor mid-chain is revoked
    revoke(mid) invalidated 2 capabilities
    P1  FAIL (P1: invalid capability handle)
    P3  FAIL (P3: derivation chain broken)
        ^ both fail, and that is deliberate. revoke_capability walks
          the derivation subtree and force-invalidates every descendant's
          table slot, so the cheap P1 check already rejects the leaf. The
          source comment is explicit that this is the point: "Without this,
          a revoked child capability's table slot remains is_valid: true and
          would pass P1 verification." So revocation is NOT a P3-only case.

  Case C: chain is longer than policy allows
    P1                    PASS
    P3 with max_depth=8   PASS
    P3 with max_depth=1   FAIL (P3: derivation chain broken)
        ^ here P1 passes and P3 fails. Delegation-depth policy is
          structural: it is a property of the chain, invisible to a token
          that looks perfectly valid on its own. Walking to the root is the
          only way to enforce it.

3. P2 is unreachable from outside rvm-cap
-----------------------------------------
  Both `CapabilityManager::verify_p2` and `ProofVerifier::verify_p2` are
  public and take `ctx: &PolicyContext` -- but rvm-cap's lib.rs declares
  `mod verify;` privately and re-exports only `ProofVerifier`, never
  `PolicyContext`. The type cannot be named by any external caller, so
  the function cannot be called. Writing the obvious thing:

      use rvm_cap::verify::PolicyContext;

  fails to compile with:

      error[E0603]: module `verify` is private

  Nothing else in the workspace re-exports it either (checked all 17
  crates). Upstream fix is one line in rvm-cap/src/lib.rs:

      pub use verify::{ProofVerifier, PolicyContext};

  Until then P2's own checks -- owner match, region bounds, lease expiry,
  nonce replay -- are reachable only from inside the crate's unit tests.

4. The tier-2 path that IS reachable: the security gate
-------------------------------------------------------
  no commitment            -> allowed at tier P1
  non-zero commitment      -> allowed at tier P2
  all-zero commitment      -> denied (PolicyViolation)  <-- a zero hash is not a proof
  require_p3, no chain     -> denied (DerivationChainBroken)

  Note the last one: the gate does not trust the caller's `p3_chain_valid`
  flag. It is set to false here and would be ignored either way -- the gate
  re-derives the answer from `p3_witness_data`, and absent data means no.

5. What the tiers cost
----------------------
  path                        ns/op    ADR target   checks
  verify_p1                     1.2        < 1 us   handle, epoch, rights
  verify_p3                     4.6          deep   + chain walk to root
  gate (P2 + witness)         336.6             -   + commitment + witness emit

Takeaway: P1 and P3 both land far inside their ADR targets, and P3 is
not dramatically dearer -- its cost grows with delegation depth, not table
size, and this chain is two hops. The gate row is the expensive one, and
nearly all of that is the witness emission measured in demo 1, not the
proof check. The reason to pick a tier is Case C, not the clock.

Two Agents That Get Closer

rvm-coherence · rvm-wasm

The coherence graph reshaping under load — and the sweep showing the merge path never fires.

cargo run -p demo-06-agents-get-closer --release 
RVM Demo 6 — Two Agents That Get Closer
Communication reshapes the partition graph.

1. Validate the agent modules
-----------------------------
  empty  8 bytes -> valid, 0 section(s)
  typed  12 bytes -> valid, 1 section(s)
  corrupt magic          -> rejected (ProofInvalid)

2. Spawn one agent into each partition
--------------------------------------
  alpha  agent 0x00a1 in partition p1  state=Running
  beta   agent 0x00b2 in partition p2  state=Running

3. Wire both partitions into the coherence engine
-------------------------------------------------
  tracking 2 partitions
  mincut backend    : stoer-wagner-builtin
  coherence backend : ratio-builtin
  thresholds        : split > 8000 bp, merge >= 4000 bp

4. Quiet: a trickle of cross-partition chatter
----------------------------------------------
  epoch 0: NoAction
      edges: p1->p1=38  p2->p2=38  p1->p2=1  p2->p1=1  
      nodes: p1[score 4871 bp, pressure 5128 bp]  p2[score 4871 bp, pressure 5128 bp]  
  epoch 1: NoAction
      edges: p1->p1=74  p2->p2=74  p1->p2=2  p2->p1=2  
      nodes: p1[score 4868 bp, pressure 5131 bp]  p2[score 4868 bp, pressure 5131 bp]  
  epoch 2: NoAction
      edges: p1->p1=108  p2->p2=108  p1->p2=3  p2->p1=3  
      nodes: p1[score 4864 bp, pressure 5135 bp]  p2[score 4864 bp, pressure 5135 bp]  

5. Loud: the two agents start talking constantly
------------------------------------------------
  epoch 3: NoAction
      edges: p1->p1=112  p2->p2=112  p1->p2=145  p2->p1=145  
      nodes: p1[score 2178 bp, pressure 7821 bp]  p2[score 2178 bp, pressure 7821 bp]  
  epoch 4: SplitRecommended p1 (pressure 8544 bp)
      edges: p1->p1=115  p2->p2=115  p1->p2=280  p2->p1=280  
      nodes: p1[score 1455 bp, pressure 8544 bp]  p2[score 1455 bp, pressure 8544 bp]  
  epoch 5: SplitRecommended p1 (pressure 8878 bp)
      edges: p1->p1=118  p2->p2=118  p1->p2=408  p2->p1=408  
      nodes: p1[score 1121 bp, pressure 8878 bp]  p2[score 1121 bp, pressure 8878 bp]  
  epoch 6: SplitRecommended p1 (pressure 9070 bp)
      edges: p1->p1=121  p2->p2=121  p1->p2=530  p2->p1=530  
      nodes: p1[score 929 bp, pressure 9070 bp]  p2[score 929 bp, pressure 9070 bp]  
  epoch 7: SplitRecommended p1 (pressure 9194 bp)
      edges: p1->p1=124  p2->p2=124  p1->p2=646  p2->p1=646  
      nodes: p1[score 805 bp, pressure 9194 bp]  p2[score 805 bp, pressure 9194 bp]  

  That is a split, not a merge. Cross-partition traffic is *external*
  weight, and cut pressure is external/total -- so the harder two partitions
  talk, the more the engine wants to pull them apart.

6. The merge signal fires -- and is then discarded
--------------------------------------------------
  evaluate_merge(p1, p2) -> mutual 4194 bp, should_merge = true
  engine.recommend()     -> SplitRecommended p1 (pressure 9194 bp)

  Both are true at once. `recommend()` scans for a split candidate first
  and returns on the first hit, so the merge branch below it is never
  reached while any partition is over pressure.

7. Is a merge reachable at all? Search the space
------------------------------------------------
  searched 4032 weight combinations
    MergeRecommended actually returned : 0
    merge signal set, split returned instead : 1244
    lowest-pressure shadowed case: self(100,0) cross(0,400)
      -> pressure p1=8333 p2=10000, mutual=4000 bp, split threshold 8000

8. Why merge is unreachable here
--------------------------------
  Across the sweep, mutual coherence and cut pressure track each other:
  mutual_bp is roughly pressure_bp - 5000. Mutual coherence divides the
  pair's shared weight by the sum of both totals, so it can only get
  large when nearly all of both partitions' traffic is with each other --
  which is exactly the condition that maximises external/total.

  So `should_merge` (>= 4000 bp) implies pressure around 9000 bp, which is
  over the 8000 bp split threshold, and `recommend()` returns the split.
  The merge arm is live code that this control flow cannot reach.

  pressure.rs already carries a comment about the merge threshold being
  lowered from 7000 to 4000 because "a threshold of 7000 (70%) was
  unreachable, preventing merge signals from ever firing". That fixed
  evaluate_merge; the shadowing in recommend() is the half still open.

  Bottom line: the split half of the coherence loop demonstrably works.
  The merge half -- the half the project leads with -- does not fire at
  this revision. Fixing it means ranking split and merge candidates
  against each other rather than returning on the first split found.

  witness records from the agent lifecycle: 2 (TaskSpawn x2)
  note: the coherence engine emits no witnesses -- graph mutation is not
        a witnessed privileged action at this revision.

Signed Hello Package

rvm-rvf

Building a signed RVForge container, then breaking it six ways.

Pack an agent, sign it, verify it, then break it.

1. Pack the agent
-----------------
  container: 448 bytes
    seg 1 type 0x07 META      payload  30 B  signed=false executable=false
    seg 2 type 0x05 MANIFEST  payload   4 B  signed=false executable=false
    seg 3 type 0x10 WASM      payload   8 B  signed=true executable=true

2. Verify with the signing key trusted
--------------------------------------
  identity  ab02777e2100766a
  448 bytes, 3 segments, ok = true
    PASS  RootManifestPresent  seg 2   RootManifestFound
    PASS  SizePolicy           -       WithinSizePolicy
    PASS  CapabilityMapping    -       CapabilitiesMapped
    PASS  ContentHash          seg 1   ContentHashMatches
    PASS  ContentHash          seg 2   ContentHashMatches
    PASS  ContentHash          seg 3   ContentHashMatches
    PASS  ExecutableSigned     seg 3   ExecutableIsSigned

3. Verify with NO trusted key
-----------------------------
  identity  ab02777e2100766a
  448 bytes, 3 segments, ok = true
    PASS  RootManifestPresent  seg 2   RootManifestFound
    PASS  SizePolicy           -       WithinSizePolicy
    PASS  CapabilityMapping    -       CapabilitiesMapped
    PASS  ContentHash          seg 1   ContentHashMatches
    PASS  ContentHash          seg 2   ContentHashMatches
    PASS  ContentHash          seg 3   ContentHashMatches
    PASS  ExecutableSigned     seg 3   ExecutableIsSigned
    SKIP  Signature            seg 3   NoTrustedKey

4. Pin the identity
-------------------
  correct expected identity          accepted
  wrong expected identity            refused  Identity/IdentityMismatch

5. Corrupt one byte at a time
-----------------------------
  flip a byte of agent bytecode      refused  ContentHash/ContentHashMismatch, Signature/SignatureRejected
  flip a byte of the signature       refused  Signature/SignatureRejected
  flip the container magic           refused  parse: BadMagic
  rewrite the capability string      refused  ContentHash/ContentHashMismatch
  signed by an untrusted key         refused  Signature/SignatureRejected
  truncate the last segment          refused  parse: Truncated

6. Capability mapping
---------------------
  declared: "network,clock"
  granted : [Network, Clock]
  denied  : 13 other classes

  tampered package: ok = false
  granted : [Network, Clock]
  ^ note this carefully. The rustdoc on `capabilities` says that when
    the capability check fails, the mapping is deny-everything. That is
    true, but it is narrower than it reads: only a CapabilityMapping
    failure zeroes it. Here ContentHash and Signature both failed, ok is
    false, and the mapping still grants Network and Clock.
    A caller must gate on `report.ok` before touching `report.capabilities`.

7. Verification is witnessed
----------------------------
  emitted 8 records for the good package, 8 for the tampered one

  seq    kind  tier      
    0  0x0051  P2
    1  0x0051  P2
    2  0x0051  P2
    3  0x0051  P2
    4  0x0051  P2
    5  0x0051  P2
    6  0x0051  P2
    7  0x0051  P2
    8  0x0051  P2
    9  0x0051  P2
   10  0x0051  P2
   11  0x0051  P2
   12  0x0051  P2
   13  0x0053  P2
   14  0x0051  P2
   15  0x0053  P2

Takeaway: every refusal in section 5 is a distinct check with its own
detail code, and the report is deterministic -- same bytes, same options,
same report. That is what makes an RVF verdict comparable across backends
rather than a local opinion.

Two traps for callers, both visible above:

  * Section 3: with no trusted key the signature check is SKIP and the
    report is still ok = true. `ok` means "nothing failed", not "the
    signature was verified". To actually require a verified signature you
    must supply a trusted key AND confirm the Signature record is Pass.
  * Section 6: `capabilities` stays populated on a failed report unless
    the capability check itself is what failed.
