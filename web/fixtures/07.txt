[1m5. Corrupt one byte at a time[0m
-----------------------------
  flip a byte of agent bytecode      [31mrefused[0m  ContentHash/ContentHashMismatch, Signature/SignatureRejected
  flip a byte of the signature       [31mrefused[0m  Signature/SignatureRejected
  flip the container magic           [31mrefused[0m  parse: BadMagic
  rewrite the capability string      [31mrefused[0m  ContentHash/ContentHashMismatch
  signed by an untrusted key         [31mrefused[0m  Signature/SignatureRejected
  truncate the last segment          [31mrefused[0m  parse: Truncated

[1m6. Capability mapping[0m
---------------------
  declared: "network,clock"
  granted : [Network, Clock]
  denied  : 13 other classes

  tampered package: ok = false
  granted : [Network, Clock]
  [33m^ note this carefully.[0m The rustdoc on `capabilities` says that when
    the capability check fails, the mapping is deny-everything. That is
    true, but it is narrower than it reads: only a CapabilityMapping
    failure zeroes it. Here ContentHash and Signature both failed, ok is
    false, and the mapping still grants Network and Clock.
    A caller must gate on `report.ok` before touching `report.capabilities`.

[33mTakeaway:[0m every refusal in section 5 is a distinct check with its own
detail code, and the report is deterministic -- same bytes, same options,
same report. That is what makes an RVF verdict comparable across backends
rather than a local opinion.

Two traps for callers, both visible above:

  * Section 3: with no trusted key the signature check is SKIP and the
    report is still ok = true. `ok` means "nothing failed", not "the
    signature was verified". To actually require a verified signature you
    must supply a trusted key AND confirm the Signature record is Pass.
  * Section 6: `capabilities` stays populated on a failed report unless
    the capability check itself is what failed.
