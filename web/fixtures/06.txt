  [33mThat is a split, not a merge.[0m Cross-partition traffic is *external*
  weight, and cut pressure is external/total -- so the harder two partitions
  talk, the more the engine wants to pull them apart.

[1m6. The merge signal fires -- and is then discarded[0m
--------------------------------------------------
  evaluate_merge(p1, p2) -> mutual 4194 bp, should_merge = true
  engine.recommend()     -> [35mSplitRecommended[0m p1 (pressure 9194 bp)

  Both are true at once. `recommend()` scans for a split candidate first
  and returns on the first hit, so the merge branch below it is never
  reached while any partition is over pressure.

[1m8. Why merge is unreachable here[0m
--------------------------------
  Across the sweep, mutual coherence and cut pressure track each other:
  mutual_bp is roughly pressure_bp - 5000. Mutual coherence divides the
  pair's shared weight by the sum of both totals, so it can only get
  large when nearly all of both partitions' traffic is with each other --
  which is exactly the condition that maximises external/total.

  So `should_merge` (>= 4000 bp) implies pressure around 9000 bp, which is
  over the 8000 bp split threshold, and `recommend()` returns the split.
  The merge arm is live code that this control flow cannot reach.

  pressure.rs already carries a comment about the merge threshold being
  lowered from 7000 to 4000 because "a threshold of 7000 (70%) was
  unreachable, preventing merge signals from ever firing". That fixed
  evaluate_merge; the shadowing in recommend() is the half still open.

  [33mBottom line:[0m the split half of the coherence loop demonstrably works.
  The merge half -- the half the project leads with -- does not fire at
  this revision. Fixing it means ranking split and merge candidates
  against each other rather than returning on the first split found.
